# Стиль кода (общий для backend и frontend)

## Комментарии и докстринги

- Докстринг — максимум одна строка и только когда имя функции не объясняет её само. По умолчанию докстринга нет.
- Комментарий — максимум одна строка, только «почему», никогда «что». Два комментария подряд, блочные комментарии `/* */` на несколько строк, многострочные докстринги запрещены.
- Проверяет `scripts/check_comments.py` в pre-commit. Не обходить.
- Вместо комментария — понятное имя, маленькая функция, тест.

## Именование

- Python: `snake_case` для функций и переменных, `PascalCase` для классов и DTO, `UPPER_CASE` для констант в `game_rules.py`.
- TypeScript: `camelCase` для функций и переменных, `PascalCase` для компонентов и типов, файлы компонентов `PascalCase.tsx`, остальные `kebab-case.ts`.
- Имена таблиц и колонок: `snake_case`, множественное число для таблиц (`receipts`, `challenges`).
- Поля JSON API: `snake_case`, как в контракте.

## Размер

- Функция — до 40 строк. Файл — до 300 строк, тесты и модули данных для тестов включительно. Если больше — разбивать по смыслу, а не по размеру.
- Один модуль — одна ответственность. Если в `service.py` появляются две несвязанные темы, это два feature-модуля.

## Ошибки

- Backend: только `AppError` из `app/core/errors.py` с кодом и HTTP-статусом. Никаких голых `HTTPException` в сервисах.
- Не глотать исключения. `except Exception: pass` запрещён.

## Что запрещено

- Мёртвый код, закомментированный код, `TODO` без ID задачи из backlog.
- `print` в коде приложения — только логгер.
- Магические числа игровых правил вне `game_rules.py`.
- Изменение чужого модуля «по пути». Нужен другой модуль — отдельная задача или явное упоминание в отчёте.
