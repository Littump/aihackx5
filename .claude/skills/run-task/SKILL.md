# run-task — полный цикл одной задачи

## Требования на входе

- Postgres поднят (`make up`), зависимости установлены (`make setup`). Проверка: `make test-be` проходит на текущем `main`.
- Роли ниже описаны как субагенты Claude Code (`.claude/agents/*.md`). Если исполнитель субагентов не умеет (другой агент, человек), роли выполняются последовательно одним исполнителем: сначала по инструкции разработчика, затем по `qa-tester.md`, затем по `reviewer.md`. Пропускать роль нельзя — QA и ревью ловят то, что разработчик не видит в своём же коде.

## Вход

ID задачи (`BE-NNN`, `FE-NNN`, `AI-NNN`, `INF-NNN`) или слово `next` — тогда взять первую задачу со статусом `todo`, у которой все зависимости `done`, в порядке эпиков из `dev/docs/backlog/README.md`.

## Шаги

1. **Контекст.** Прочитать `CLAUDE.md`, `dev/docs/backlog/README.md`, файл эпика задачи. Выписать acceptance criteria и зависимости. Если зависимость не `done` — остановиться и сказать об этом.
2. **Статус.** В `dev/docs/backlog/README.md` поставить задаче `in_progress`.
3. **Разработка.** Запустить субагента `backend-dev` или `frontend-dev` (по префиксу задачи; `AI-` — backend-dev с указанием прочитать `.claude/rules/backend.md` раздел LLM; `INF-` — сделать самому). Передать: ID задачи, acceptance criteria дословно, список файлов из описания задачи, напоминание про скиллы `add-endpoint` / `add-model` / `add-logic` / `add-screen` / `update-api-contract`.
4. **Тестирование.** Запустить `qa-tester` с ID задачи и отчётом разработчика. Если вердикт `FAIL` — вернуть дефекты тому же разработчику (в Claude Code — SendMessage тому же агенту, контекст сохраняется; без субагентов — просто следующий круг с тем же списком дефектов), потом снова `qa-tester`. Максимум 3 круга; после третьего — остановиться и показать дефекты пользователю.
5. **Ревью.** Запустить `reviewer` с ID задачи и `git diff --stat`. `REQUEST_CHANGES` — вернуть разработчику, повторить шаг 4 в сокращённом виде (только затронутые тесты). Максимум 2 круга.
6. **Проверка самому.** `make check` и профильные тесты. Посмотреть вывод глазами.
7. **Закрытие.** Статус `done` в `dev/docs/backlog/README.md`, дата. Если менялась схема или контракт — убедиться, что `data-model.md` / `openapi.yaml` / `schema.d.ts` обновлены.
8. **Коммит.** Один коммит на задачу, сообщение на русском: `BE-012: обработка чека обновляет прогресс челленджа`. Тело пустое. Push только если пользователь просил работать с push.

## Выход

Короткий отчёт пользователю: что сделано, какие файлы, сколько тестов, что не вошло, следующая задача по backlog.

## Если что-то не так

- Задача требует менять чужой модуль вне описания — сделать, но явно перечислить в отчёте.
- Acceptance criteria противоречат PRD или domain-rules — не гадать, спросить.
- Тесты падают из-за инфраструктуры (нет Postgres, нет node_modules) — `make up`, `make setup`, затем повторить. Не отключать тесты.
