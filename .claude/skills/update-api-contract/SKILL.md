# update-api-contract — контракт как источник истины

Контракт живёт в `dev/contracts/openapi.yaml`. Backend его реализует, frontend по нему генерирует типы. Порядок всегда: контракт → backend → типы → frontend.

## Шаги

1. **Правка YAML.** Изменить путь/схему в `openapi.yaml`. Схемы — в `components/schemas`, переиспользовать через `$ref`. Поля `snake_case`, обязательные поля в `required`. Не удалять поля, которые уже использует фронт, без правки фронта в той же задаче.
2. **Валидация YAML.** `make contract-lint` (проверка, что файл парсится и ссылки резолвятся).
3. **Backend.** Обновить `dto.py` и, если нужно, `service.py`/`router.py`. Запустить `make contract-check` — скрипт `dev/backend/scripts/export_openapi.py` выгружает схему приложения и сравнивает пути и поля с контрактом. Расхождения — чинить в коде, а не в контракте, если контракт менялся осознанно.
4. **Типы фронта.** `make contract-types` → `dev/frontend/src/shared/api/schema.d.ts`. Файл генерируется, руками не править, коммитится.
5. **Frontend.** `npm run check` покажет, где типы разъехались. Поправить `api.ts`/компоненты.
6. **Документация.** Если добавилась ручка — строка в таблице `dev/docs/api-contract.md`.
7. **Тесты.** e2e на изменённую ручку проверяет новые поля. Тест экрана на фронте — новые данные.

## Правила формы

- Ответ-агрегат для экрана (`HomeResponse`) собирает вложенные схемы (`DomovoyState`, `ChallengeDto`), а не дублирует поля.
- Даты — ISO-8601 строки, деньги — числа с двумя знаками (`number`, `format: decimal`), баллы и XP — `integer`.
- Ошибки — единая схема `Error` с `error.code` и `error.message`.
- Демо-параметры (`user_id` в пути) — как обычные параметры; auth в MVP нет.
