# Архитектурные решения

Короткий журнал решений, чтобы не переспоривать их заново. Формат: решение → почему → чем платим.

## 1. Монолит FastAPI, синхронная обработка чека в запросе
**Почему:** демо и тесты должны быть детерминированными: чек либо обработан целиком, либо нет. Очередь добавила бы асинхронность, которую нечем показать и сложно тестировать за четыре дня.
**Платим:** `POST /receipts` работает десятки миллисекунд вместо единиц; при реальной нагрузке шаги 3–8 из `architecture.md` уехали бы в воркер.

## 2. Raw SQL через psycopg 3, без ORM
**Почему:** схема маленькая, запросы простые, а ORM прячет от агента и ревьюера, какой SQL реально выполняется. Явный SQL в одном файле на feature проще проверить и объяснить жюри.
**Платим:** руками пишем `INSERT ... RETURNING` и списки колонок; миграции — просто SQL-файлы вперёд.

## 3. Pydantic на всех границах слоёв
**Почему:** словари не проверяются, dataclass не валидирует, а pydantic даёт и типы, и валидацию JSONB, и `from_attributes` для DTO. Одна технология для строк базы, доменных объектов и API.
**Платим:** чуть больше классов; `Decimal` в DTO надо явно приводить к `float`.

## 4. Контракт до кода
**Почему:** frontend и backend делает один человек по очереди, а экраны нужны раньше ручек. `openapi.yaml` + MSW позволяют верстать против контракта, `contract-check` не даёт им разъехаться.
**Платим:** любое изменение API — три шага (YAML, backend, типы), а не один.

## 5. Управляемое время через `app/core/clock.py`
**Почему:** синтетика — это недели истории, а челленджи и лига считаются «с понедельника». Демо через неделю после генерации без замороженного времени показало бы пустую неделю. Ruff запрещает `datetime.now()` вне `clock.py`.
**Платим:** одна лишняя функция в импортах; в тестах — фикстура `freeze_time`.

## 6. Все числа в `game_rules.py` и `domain-rules.md`
**Почему:** экономика наград и антифрод должны быть объяснимы на демо: жюри спросит «откуда 40 %», и ответ должен быть в одном месте, а не размазан по сервисам.
**Платим:** документ и модуль нужно держать синхронными; на это есть тест в BE-003.

## 7. Награды детерминированы, случайных призов нет
**Почему:** случайные суперпризы вызывают недоверие (кейс Ozon «Морковск») и тянут за собой правила стимулирующих мероприятий и лотерей. Детерминированная награда за инкремент считается экономикой и объясняется одной фразой.
**Платим:** меньше «вау» на экране, чем у колеса фортуны; компенсируем персонажем и лигой.

## 8. Рейтинг привязан к магазину, а не к адресу
**Почему:** кейс запрещает ФИО и адреса; любимый магазин — публичная сущность, которой хватает для «соседей». Внутри — лиги по 30 человек по активности (принцип Duolingo), наружу — только псевдоним, уровень, score, ранг.
**Платим:** «дом» условный: соседи по подъезду могут попасть в разные лиги одного магазина.

## 9. Antifraud precision-first с явными порогами
**Почему:** критерий кейса — precision важнее recall, порог должен быть объясним. Взвешенные сигналы с текстовым `detail` и правило «блок только при двух сильных сигналах» объясняются продакту за минуту; ML на синтетике ничего бы не добавил.
**Платим:** recall около 0.6, хвост ловится отложенной наградой, а не блоком.

## 10. Auth в MVP нет, пользователь — `user_id` в пути
**Почему:** демо переключает пользователей с одного экрана; интеграция с X5 ID вне скоупа хакатона.
**Платим:** приложение нельзя выставлять наружу без прокси с базовой защитой — учтено в задачах деплоя (`E13`).

## 11. Один VM в Yandex Cloud, docker compose, CD через GitHub Actions по SSH
**Почему:** один хост держит Postgres, backend и frontend за nginx; сборка образов в Actions, на VM только `pull` и `up`. Kubernetes и managed-сервисы для четырёхдневного демо — лишние.
**Платим:** нет отказоустойчивости; при падении VM демо не работает. Бэкап базы — `pg_dump` по cron в задаче деплоя.
