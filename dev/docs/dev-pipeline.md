# Pipeline разработки

## Единица работы — задача из backlog

Каждая задача в `dev/docs/backlog/E*.md` имеет: ID (`BE-`, `FE-`, `AI-`, `INF-`), владельца, зависимости, описание, список файлов, acceptance criteria, требования к тестам. Доска со статусами — `dev/docs/backlog/README.md`. Статусы: `todo` → `in_progress` → `review` → `done`, плюс `blocked`.

## Цикл одной задачи (скилл `run-task`)

```
backlog ──▶ контекст ──▶ разработчик ──▶ QA ──▶ ревьюер ──▶ проверка ──▶ done + коммит
             (правила)   backend-dev     qa-tester  reviewer   make check
                         frontend-dev       │          │
                              ▲─────FAIL────┘          │
                              ▲──────REQUEST_CHANGES───┘
```

1. **Контекст.** Агент читает `CLAUDE.md`, правила, эпик задачи. Зависимости не `done` — стоп.
2. **Разработчик** пишет код по слоям и по скиллам, базовые тесты, гоняет `make check` и тесты. Не коммитит.
3. **QA** дописывает тесты по acceptance criteria и контракту, ищет дефекты, отдаёт список. До 3 кругов.
4. **Ревьюер** проверяет правила (слои, SQL, докстринги, числа, контракт, документация) с `file:line`. До 2 кругов.
5. **Оркестратор** сам запускает `make check` и тесты, смотрит вывод, обновляет статус и делает один коммит.

Человек делает то же самое руками или запускает `/run-task <ID>` и смотрит результат.

## Ветки и коммиты

- Хакатон, два человека, разные зоны кода — работаем в `main` с ребейзом: `git pull --rebase` перед пушем.
- Один коммит на задачу. Заголовок: `BE-012: обработка чека обновляет прогресс челленджа`. Тело пустое.
- Pre-commit обязателен: `make setup` ставит хуки. Хук отформатировал файлы — `git add` и коммит повторно.
- Ломать чужую зону нельзя: если задача трогает файлы другого владельца — сначала сообщение ему.

## Что считается done

См. `.claude/rules/testing.md`, раздел Definition of Done. Коротко: критерии выполнены, тесты есть и зелёные, `make check` зелёный, документы обновлены, статус на доске обновлён.

## Порядок эпиков

`E0 Foundation` → `E1 Synthetic` и `E2 Receipts & Features` параллельно → `E3 Savings`, `E4 Domovoy`, `E5 Challenges` → `E6 Frontend core` → `E7 League`, `E8 Referral & Antifraud` → `E9 Frontend social` → `E10 PM view` → `E11 Eval & Simulation` → `E12 Demo`. Точный порядок и зависимости — на доске.

## Стыковка backend ↔ frontend

Контракт `dev/contracts/openapi.yaml` пишется в `E0` для всех ручек MVP. Frontend делает экраны против контракта с MSW-моками, не дожидаясь ручек. Когда ручка готова — мок выключается. Любое изменение формы ответа — через скилл `update-api-contract`.

## Стыковка core ↔ AI/данные

Интерфейсы зафиксированы в `team.md`: синтетика пишет в таблицы по `data-model.md`; LLM-модуль — функция `llm.domovoy_copy.render_challenge(...)` с фиксированной сигнатурой и fallback; eval и simulation читают базу и пишут `eval_runs` / `simulation_runs`. Пока модуля нет — работает fallback-шаблон, core не блокируется.
